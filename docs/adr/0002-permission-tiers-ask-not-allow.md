# 权限档位只放宽「是否询问」，不放宽「是否允许」

Status: accepted (2026-10-11)

工具审批新增三档全局设置（默认 / 只读放行 / 全放行），配置键 `permissions.toolPolicy`
（`'default' | 'readonly' | 'open'`）。实现上只在 `createRegistryAuthorizer` 的
`needsConfirm` 表达式里替换 `reg.approval === 'ask'` 这一项，`assess` 的 `ask` 与 `deny` 一律不动：
无论档位开到哪一档，「越出工作区」照旧弹窗征求一次明确同意，「策略拒绝」与「未注册工具」永远拒绝。
档位只决定**要不要问人**，不决定**允不允许**。

## Considered Options

- **档位也覆盖越界（`assess` 的 `ask`）**：否决。工作目录之外是用户的整个磁盘，而仓库已声明
  「工作目录本身不构成 OS 隔离」（`PROJECT_STATE.md:65`）；让一个设置项吃掉这道边界，等于「全放行」
  档一次性废掉唯一真实的边界。
- **只读放行档信任第三方自述的 `risk:'read'`**：否决。skill 的 risk 来自 manifest 自述，放行它等于让
  一个自称只读的第三方脚本免确认执行；第三方来源的 `approval:'ask'` 是有意设下的不变量。
- **全放行档为 `risk:'exec'` 保留一道闸**：否决。用户选的档位名就是「全部」；且工作区内的 shell 一样
  能碰全盘，单独留下 exec 只是仪式感。
- **把档位判定挪到 main（组装 authorizer 前先改注册表元数据）**：否决。审批决策是纯策略，留在 core 的
  单一表达式里才能零依赖单测（`registry.test.ts` 已是这条链的回归面）。

## Consequences

- 「全放行」档会连 `shell`、MCP 工具、第三方 skill 一并放行——**这是有意的破例**，与
  `DEV_PLAN.md:255`「高影响或不可逆操作需单独审批」相反，该句在本档位上被本 ADR 取代。代价是拆掉
  skill 自述三道防线（默认禁用 + 内容指纹 + 每次调用审批）中的第三道，须在设置页显著警示。
- 设置页里三处「每次调用都要确认」的文案（联网 `WebSection` / 技能 `SkillsSection` / MCP `McpSection`）
  在非默认档下不再成立，必须随档位改写。
- 档位在**下一次发消息**时生效（`chat.ts` 每轮重取注册表）；在途弹窗与在途那轮对话不受影响。
  这不是巧合而是设计：让切档能吃掉在途请求，等于开出一条「用设置页绕过一次审批」的路径。
- 不提供「总是允许此工具」这类按工具记忆。档位已是全局粗粒度开关，再叠一层细粒度记忆会让
  「我现在到底放行了什么」无法回答。
- 默认档是现状的逐字复刻（含 `get_current_time`、`web_search` 等纯读工具的 `approval:'ask'`），
  存量用户升级后行为零变化；纯读免打扰是「只读放行」档的职责。
